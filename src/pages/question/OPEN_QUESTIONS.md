## BE-1: Google 인증 및 세션 계약

- 계약: Notion 세호 담당 명세(로그인·토큰 재발급·로그아웃). Google Identity Services의 ID 토큰을 `POST /api/auth/login`에 `id_token`으로 보내고, 응답의 `next_step`(ONBOARDING·SURVEY·HOME)으로 이동한다. 실서버는 snake_case로 받고 돌려준다(2026-11-13 확인). Swagger 스키마의 camelCase 표기와 다르다.
- 현재: `VITE_API_MODE=server`일 때만 실제 로그인을 쓴다(`src/lib/api`, `src/lib/auth`). 이 값이 없으면 버튼은 예전처럼 인증 없이 학교 정보 화면으로 이동하며 토큰을 만들지 않는다.
- 토큰: 액세스 토큰은 메모리에만, 리프레시 토큰은 sessionStorage에 둔다. 새로고침하면 리프레시 토큰으로 세션을 복구하고, 탭을 닫으면 다시 로그인한다.
- 확인: 2026-11-13 등록된 학교 Google 계정으로 `http://localhost:5173`에서 실제 로그인 성공(프로젝트 담당자 확인). 신규 계정이라 `next_step=ONBOARDING`만 실제로 확인했고, SURVEY·HOME 이동은 자동 테스트로만 검증했다.

## BE-9: 설문 답변 저장

- 현재(서버 모드, 2026-11-14): 설문 화면과 결과 화면은 세션마다 한 번 `GET /api/surveys/current`, `GET /api/me/survey`를 읽는다. 저장된 답변은 아직 답한 것이 없을 때만 화면에 채우고, 그 revision을 다음 저장의 `expected_revision`으로 쓴다. 마지막 질문 다음 로딩 화면에서 `PUT /api/me/survey`로 16개 답변과 우선순위를 저장하고, 성공한 뒤에만 결과로 넘어간다. 샘플 모드는 예전처럼 메모리에만 둔다.
- 코드: 화면은 Figma 문구를 그대로 쓰고, 문항과 선택지는 `src/lib/survey/surveyCodes.ts`의 표로 `question_code`·`option_code`에 연결한다. 배열 순서로 연결하지 않는다. 코드는 실서버 응답(2026-11-14)을 기준으로 했다. Figma와 실서버 문구가 다른 선택지 2개는 `LABEL_DIFFERENCES`에 적었다(DE-7).
- `BEDTIME_H`(2026-11-14 실서버 확인): 서버가 Figma와 같은 문구의 5개 선택지 `BEFORE_22`, `FROM_22_TO_24`, `FROM_00_TO_02`, `AFTER_02`, `IRREGULAR`를 보낸다. Notion 복제본은 동기화되지 않아 아직 7개로 적혀 있다. 서버 설문이 화면과 다르면(문항·코드·선택지 개수) 해당 문항에 안내를 보이고 저장을 막는 보호 장치는 그대로 둔다.
- 409 `SURVEY_REVISION_CONFLICT`: 저장된 설문을 다시 읽고, 화면의 답변은 그대로 둔 채 `지금 답변으로 저장`과 `저장된 답변 보기` 중 하나를 고르게 한다. 자동으로 다시 저장하거나 덮어쓰지 않는다.
- 우선순위: 새 세션(다시 로그인)의 첫 설문은 `GET /api/me/survey`의 `priorities`를 쓴다. 실서버는 첫 제출 전에 `revision: 0`, `priorities: []`, `answers: []`를 보낸다(2026-11-14 확인). 그래서 온보딩을 저장하고 설문 전에 이탈한 사용자는 다시 로그인하면 우선순위를 읽을 방법이 없다(`GET /api/me/profile`은 설문 전 409, 로그인 응답에는 우선순위가 없다). 임시 대응: 질문 전에 우선순위 단계로 보내 다시 고르게 하고 설문 저장에 함께 보낸다(온보딩의 다른 답이 메모리에 없어 온보딩 저장은 보내지 않는다). 같은 세션에서 온보딩을 마친 경우는 메모리의 우선순위를 그대로 쓴다.
- 홈 `내 설문 다시보기`는 마이페이지로 이동한다(2026-11-14 결정). 홈에서는 설문을 저장하지 않는다.
- 실서버 확인(2026-11-14, 테스트 계정): 최초 `PUT /api/me/survey`가 `SURVEY_SAVE_SUCCESS`, `revision: 1`, `survey_completed: true`, `next_step: HOME`을 돌려줬고, 새로고침 후 `GET /api/me/survey`가 우선순위 5개(1~5순위)와 답변 16개를 그대로 돌려줬다. 재설문 저장(revision 증가)과 409 충돌은 실서버에서 아직 확인하지 않았다(자동·목업 테스트만).
- 백엔드 요청: 첫 설문 제출 전에도 `GET /api/me/survey`의 `priorities`에 온보딩(`PUT /api/me/onboarding`)에서 저장한 순위를 담아 달라(명세의 `priorities`는 선택한 3~5개 카테고리와 순위를 반환한다는 설명과 같다). 반영되면 프론트엔드 변경 없이 다시 고르는 단계가 사라진다.
- 질문: 새로고침·이탈 후 미제출 답변을 어디까지 복원하는가(명세의 논의 필요 항목)?

## 기존 코드가 참조하는 추가 질문

아래 항목은 기존 주석의 ID와 주제를 보존한 확인 질문이다. 원본 질문 문서가 발견되면 의미와 세부 내용을 대조한다.

- **BE-3:** 단계 가드는 입력 완료 여부만 검사한다. 인증은 서버 모드에서 `src/components/auth/RequireAuth.tsx`가 따로 검사한다: 로그인 화면(`/`)과 공유 화면(`/share`)을 뺀 모든 화면은 세션이 없으면 로그인 화면으로 보낸다. 로그인하거나 세션이 끝나면(로그아웃·재발급 실패) 화면을 다시 마운트해 이전 세션의 메모리 입력을 지운다. 새로고침 후 서버에 닿지 못해 세션을 확인하지 못하면 보호 화면을 열지 않고 로그인 화면으로 보낸다(저장된 토큰은 남겨 다음 새로고침에서 다시 확인). 로그인한 사용자가 `/`를 열면 로그인 화면을 그대로 보여준다(로그인 응답 외에는 `next_step`을 알 방법이 없음).
- **BE-7:** 저장 성공 이후 이동과 실패 시 재시도는 어떻게 처리하는가? `CompletePage.tsx`가 BE-6과 함께 참조한다. 답변 전에는 저장 성공을 가정하지 않는다.
- **PL-1:** 기숙사 방 인원의 지원 범위는 무엇인가? 현재 선택지를 유지하고 임의로 제한하지 않는다.
- **PL-3:** 선택 개수는 최소 3개, 최대 5개다(2026-11-09 결정, 2026-11-13 QA 3 검토 후 프로젝트 담당자가 유지). 캐릭터 외형은 1~3순위만 반영한다. 미션 안내는 Figma `1041:30715`의 `생활습관 5개의 순위를 매겨주세요!`를 따른다(#60). 해제 시 뒤 순위를 앞당기는 규칙은 아직 확정되지 않았다.
- **DE-9:** Figma의 순위 배지는 1~3만 있다. 4·5순위는 같은 원형 배지에 Pretendard 숫자로 표시한다. 완료 화면은 Figma에 순위 배지 없이 카드 3장만 있다. 사용자 결정에 따라 모든 카드에 같은 순위 배지를 붙이고, 4장 이상이면 선택 화면처럼 두 번째 줄에 놓고 캐릭터를 그 높이만큼 줄인다. 디자이너가 배지와 배치를 확정해야 한다.
- **PL-4:** 생활습관 카테고리의 기본·선택 상태 명칭은 무엇인가? 답변 전에는 기존 라벨을 유지한다.
- **DE-5:** 기숙사 자동완성의 상태별 UI와 안내 문구는 무엇인가? 현재 임시 UI를 유지하며 최종 디자인으로 간주하지 않는다.

## PL-7: 공유 링크의 저장 방식

- 현재: 서버가 없어 공유 링크(`/share#...`)의 해시에 이름, 학과, 우선순위, 답변 번호를 담는다. 해시는 서버로 전송되지 않는다. 나이와 매칭률은 담지 않는다(Figma 메모 `1952:40096`: 나이 빼기).
- 공유 화면: Figma `1952:39744`. 매칭률은 `??%`, 처음 열면 `복작복작으로 이동하기` 안내 팝업(`1952:40072`)을 띄우고, 답변 카드는 2개까지 보여준 뒤 나머지를 흐리게 처리하고 같은 안내를 보여준다. 이동 버튼과 `홈화면으로 가기`는 로그인 화면으로 간다. 흐림 영역 안내의 Figma 버튼은 `취소하기`/`확정하기`라 문맥이 맞지 않아 단일 `복작복작으로 이동하기`로 바꿨다.
- 카카오톡: 링크만 붙여 넣으면 카카오톡은 페이지의 공통 제목(`복작복작`)만 미리보기로 보여준다. 이름이 들어간 카드는 PL-6의 카카오톡 공유로 보낸다.
- 질문: 공유 데이터를 서버에 저장하고 짧은 링크를 만들 것인가? 링크에 이름과 학과가 담겨도 되는가? 카카오 앱 키와 템플릿은 누가 준비하는가?
- 답변 전: 해시 방식을 임시로 유지한다.

## PL-8: QA용 설문 건너뛰기

- 답변 전: QA 기간에만 쓰는 임시 기능으로 유지한다.
