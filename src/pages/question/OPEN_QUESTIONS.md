## BE-1: Google 인증 및 세션 계약

- 현재: Google 버튼은 인증 없이 학교 정보 화면으로 이동하며 로그인 상태와 토큰을 만들지 않는다.
- 질문: 인증 시작·콜백 경로, 세션 전달 방식, 실패 처리, 기존 가입자 분기는 어떻게 정의하는가?
- 답변 전: 현재 임시 이동을 유지하고 실제 인증 성공으로 설명하지 않는다.

## BE-6: 온보딩 저장과 완료 처리

- 현재: 입력은 메모리에만 있고 새로고침하면 초기화된다. 서버 저장은 연결되지 않았다.
- 질문: 단계별 저장 또는 최종 일괄 저장 중 무엇을 사용하는가? 요청·응답 형식, 실패 시 재시도, 완료 후 목적지는 무엇인가?
- 답변 전: 서버 저장이나 영속화를 임의로 추가하지 않는다.

## BE-8: 입력값 검증 정책

- 현재: 단계별 필수값을 검사하며 코드 주석에서 서버 계약 미합의를 명시한다.
- 질문: 학과·학번·이름·출생연도·성별·방 정보의 필수 여부와 허용 범위, 서버 오류 형식은 무엇인가?
- 답변 전: 기존 검증을 유지하고 확정된 서비스 정책으로 간주하지 않는다.

## BE-4: 생활습관 우선순위 전달 형식

- 현재: 우선순위는 `CategoryId[]`로 관리하고 `priority.ts`에서 완료 여부를 검사한다.
- 질문: 서버의 카테고리 ID와 프론트 ID는 일치하는가? 순서는 배열 위치와 별도 rank 중 어떻게 전달하는가?
- 답변 전: 기존 카테고리와 검증을 유지하고 서버 DTO는 확정하지 않는다.

## BE-5: 기숙사 검색·생성 API

- 현재: `DormitoryApi`는 `search(query)`와 `create(name)`, 결과는 `{ id, name }` 형태를 가정한다. 실제 서버 구현은 미연결이며 생성은 실패 처리한다.
- 질문: 검색·생성 엔드포인트, 학교별 검색 범위, 최소 검색 길이, 중복 생성 정책, 응답·오류 형식은 무엇인가? 저장 시 ID와 이름 중 무엇을 전달하는가?
- 답변 전: 현재 인터페이스를 임시 연결 경계로 유지한다. mock은 개발·시연 환경에서만 사용한다.
- 참고: 이 ID는 `dormitoryApi.ts`의 기존 `OPEN_QUESTIONS BE-5` 주석과 대응한다.

## DE-6: 상황 화면 전환 방식

- 결정 내용: Figma 프로토타입 `1377:49785`를 따른다. 주제마다 STEP 화면(전체 일러스트, `STEP n`, 상황 문구)을 2초 보여준 뒤 0.8초 디졸브로 질문 화면으로 넘어간다. 질문 화면의 `상황 보기`를 누르면 `질문 다시보기` 버튼이 있는 STEP 화면이 디졸브로 뜨고, `질문 다시보기`로 돌아온다. 버튼 문구는 Figma의 `질문 보기` 대신 프로젝트 담당자 요청(2026-11-10)에 따라 `질문 다시보기`로 쓴다. 질문 번호는 `Q1-1`(나), `Q1-2`(룸메이트) 형식이다.
- 답변 근거 및 날짜: 프로젝트 담당자 요청, 2026-11-10. 이전 결정(2026-11-07, 상황 문구 2초 후 시트가 올라오는 방식)을 대체한다.
- 영향 파일: `src/pages/question/QuestionPage.tsx`, `src/pages/question/questionData.ts`, `src/pages/question/question.test.tsx`
- 임시 구현(미확정): 답한 질문으로 돌아오면 STEP 화면을 다시 보여주지 않는다. 룸메이트 질문은 STEP 화면 없이 바로 표시하지만 `상황 보기`로 열 수 있다. `상황 보기`로 연 STEP 화면은 자동으로 닫히지 않는다.

## DE-12: 설문 결과 카드의 매칭률과 나이

- 현재: 로딩 다음 설문 결과(`/question/profile`)는 Figma `1377:35804` 상세 프로필 화면이다. 카드에는 온보딩에서 입력한 이름, 학과, 출생년도로 계산한 나이, 내 캐릭터를 보여주고 아래에 내 답변 요약을 둔다.

## 기존 코드가 참조하는 추가 질문

아래 항목은 기존 주석의 ID와 주제를 보존한 확인 질문이다. 원본 질문 문서가 발견되면 의미와 세부 내용을 대조한다.

- **BE-3:** 현재 단계 가드는 입력 완료 여부만 검사한다. 인증 연동 후 비로그인 사용자와 세션 만료를 어떻게 처리하는가? 답변 전에는 입력 가드를 인증으로 취급하지 않는다.
- **BE-7:** 저장 성공 이후 이동과 실패 시 재시도는 어떻게 처리하는가? `CompletePage.tsx`가 BE-6과 함께 참조한다. 답변 전에는 저장 성공을 가정하지 않는다.
- **PL-1:** 기숙사 방 인원의 지원 범위는 무엇인가? 현재 선택지를 유지하고 임의로 제한하지 않는다.
- **PL-3:** 선택 개수는 최소 3개, 최대 5개다(2026-11-09 결정, 2026-11-13 QA 3 검토 후 프로젝트 담당자가 유지). 캐릭터 외형은 1~3순위만 반영한다. 미션 안내는 Figma `1041:30715`의 `생활습관 5개의 순위를 매겨주세요!`를 따른다(#60). 해제 시 뒤 순위를 앞당기는 규칙은 아직 확정되지 않았다.
- **DE-9:** Figma의 순위 배지는 1~3만 있다. 4·5순위는 같은 원형 배지에 Pretendard 숫자로 표시한다. 완료 화면은 Figma에 순위 배지 없이 카드 3장만 있다. 사용자 결정에 따라 모든 카드에 같은 순위 배지를 붙이고, 4장 이상이면 선택 화면처럼 두 번째 줄에 놓고 캐릭터를 그 높이만큼 줄인다. 디자이너가 배지와 배치를 확정해야 한다.
- **PL-4:** 생활습관 카테고리의 기본·선택 상태 명칭은 무엇인가? 답변 전에는 기존 라벨을 유지한다.
- **DE-5:** 기숙사 자동완성의 상태별 UI와 안내 문구는 무엇인가? 현재 임시 UI를 유지하며 최종 디자인으로 간주하지 않는다.

## PL-7: 공유 링크의 저장 방식

- 현재: 서버가 없어 공유 링크(`/share#...`)의 해시에 이름, 학과, 우선순위, 답변 번호를 담는다. 해시는 서버로 전송되지 않는다. 나이와 매칭률은 담지 않는다(Figma 메모 `1952:40096`: 나이 빼기).
- 공유 화면: Figma `1952:39744`. 매칭률은 `??%`, 처음 열면 `복작복작으로 이동하기` 안내 팝업(`1952:40072`)을 띄우고, 답변 카드는 2개까지 보여준 뒤 나머지를 흐리게 처리하고 같은 안내를 보여준다. 이동 버튼과 `홈화면으로 가기`는 로그인 화면으로 간다. 흐림 영역 안내의 Figma 버튼은 `취소하기`/`확정하기`라 문맥이 맞지 않아 단일 `복작복작으로 이동하기`로 바꿨다.
- 카카오톡: 링크만 붙여 넣으면 카카오톡은 페이지의 공통 제목(`복작복작`)만 미리보기로 보여준다. Figma의 미리보기(이름이 들어간 문구와 이미지)는 카카오 SDK의 메시지 템플릿이나 서버에서 만든 미리보기 태그가 필요하다. 저장소와 배포 설정에 카카오 앱 키, 등록 도메인, 템플릿이 없다.
- 질문: 공유 데이터를 서버에 저장하고 짧은 링크를 만들 것인가? 링크에 이름과 학과가 담겨도 되는가? 카카오 앱 키와 템플릿은 누가 준비하는가?
- 답변 전: 해시 방식을 임시로 유지한다.
