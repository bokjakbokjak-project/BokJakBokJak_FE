# 핵심 체험 | 전체 서비스

`복작복작_체험용_전체서비스_Claude_구현요청.md`(2026-11-20)의 프론트엔드 1차 구현이다. 작업 브랜치는 `feature/experience-mode`(기준: `feature/user-test`)이며, main 병합이나 운영 배포는 승인되지 않았다.

## 1. 구조

- **빌드 설정과 런타임 모드를 분리했다.** `VITE_API_MODE`는 그대로 배포의 연결 설정이다. `VITE_EXPERIENCE=true`인 빌드에서만 상단에 `핵심 체험 | 전체 서비스` 전환이 나오고, 선택한 모드는 이 브라우저의 localStorage(`bokjak-app-mode`)에 남는다. 운영 빌드에는 이 값을 넣지 않는다.
- **핵심 체험**은 기존 샘플 흐름(서버 요청 없음, 로그인 없음)을 그대로 쓴다. `getApiMode()`가 체험 모드에서 `mock`을 돌려주므로 인증·추천·채팅 화면이 모두 샘플 경로를 탄다. 여기에 체험 전용 시작 화면, 예시 답변 건너뛰기, 자동 응답 체험 채팅, 진행자 메뉴를 더했다.
- **전체 서비스**는 배포된 앱 그대로다(실제 Google 로그인과 서버).
- **전환은 페이지를 다시 불러온다.** 다른 모드의 시작 화면으로 `location.replace`하므로 진행 중 요청, 채팅 폴링, 예약된 자동 응답, 메모리 상태와 캐시가 한 번에 정리되고, 늦게 온 응답이 새 모드에 닿지 않는다. 전환 전에 저장하지 않은 입력이 사라진다고 묻는다.

## 2. 진입 방법

| 링크                       | 동작                                                               |
| -------------------------- | ------------------------------------------------------------------ |
| `/experience`              | 핵심 체험 시작 화면(부스 QR용). 이전에 쓴 모드보다 링크가 우선한다 |
| `/experience?purpose=film` | 촬영 진행(진행자 메뉴에 장면 이동, 채팅 안건 2개)                  |
| `/service`                 | 전체 서비스 로그인(심사 링크용)                                    |
| 상단 전환                  | 어느 화면에서든 다른 모드의 시작 화면으로                          |

`VITE_EXPERIENCE`가 없는 빌드에서는 두 링크 모두 첫 화면(`/`)으로 간다.

### 로컬 실행

```bash
npm run usertest            # http://localhost:5173, .env.usertest에 VITE_EXPERIENCE=true 포함
```

## 3. 체험 데이터와 실제 서버 데이터의 경계

| 기능          | 핵심 체험                                       | 사용자 테스트(전체 서비스 + `VITE_USER_TEST`) | 전체 서비스        |
| ------------- | ----------------------------------------------- | --------------------------------------------- | ------------------ |
| 인증          | 없음(로컬 체험 세션)                            | 실제 Google 로그인                            | 실제 Google 로그인 |
| 기본 정보     | 체험용 공통값(`체험자`, `체험학과`…)            | 테스트 공통값                                 | 실제 입력          |
| 우선순위·설문 | 이 기기에만 저장, `예시 답변으로 건너뛰기` 가능 | 서버 저장                                     | 서버 저장          |
| 추천·분석     | 예시 후보(매칭률 원에 `예시`, 목록에 안내)      | 서버 결과                                     | 서버 결과          |
| 채팅          | 체험 채팅(자동 응답)                            | 체험 채팅(실제 분석의 조율 항목 기준)         | 실제 채팅          |
| 최종 매칭     | 체험 상태(홈 반영)                              | 체험 상태(홈 반영)                            | 서버 CONFIRMED     |

- 체험 채팅은 채팅·매칭 API를 하나도 부르지 않는다. 대화 시작 전에 `이후 대화는 자동으로 응답하는 체험 상대와 진행돼요. 실제 사용자에게 대화 요청이나 메시지가 전송되지 않아요.`를 띄운다.
- 체험 채팅의 안건은 분석의 `이런 점은 조율해봐요` 문구로 고른다(청소, 잠드는 시간, 알람). 맞는 안건이 없으면 그 후보에게 없는 갈등을 만들지 않고, 예시 두 사람(나와 김혜나, 청소 주기)으로 바뀐다고 안내한 뒤 진행한다.
- 합의문은 준비된 `합의 예시`다. 대화에서 생성한 것이 아니다.
- 안건 완료와 최종 매칭은 따로다. `매칭 확정하기` 뒤 체험 상대도 확정해야 `매칭이 완료됐어요!`가 된다. 체험 매칭은 서버에 저장하지 않는다.
- 체험 세션은 로그인 없는 경우 `demoSessionId`(무작위 UUID)로, 사용자 테스트에서는 회차·참여자별로 localStorage에 둔다. 실제 사용자 ID를 만들어 쓰지 않는다.
- 체험 결과의 후보 ID(`hyena` 등)는 샘플 데이터의 ID이며 실제 API로 가지 않는다. 사용자 테스트에서 실제 후보를 체험 채팅 상대로 쓸 때는 이름과 분석 문구만 스냅샷으로 남기고, ID는 분석 화면을 다시 여는 데만 쓴다.

## 4. 촬영 · 사용자 테스트 · 부스

| 목적          | 시작                                                               | 초기화                                                                                             |
| ------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 부스          | `/experience` → `체험 시작하기`                                    | 진행자 메뉴(오른쪽 위 `⋯`)의 `다음 참가자`                                                         |
| 촬영          | `/experience?purpose=film` 또는 진행자 메뉴 `촬영 진행으로 바꾸기` | 진행자 메뉴 `처음부터`, `장면 이동`(우선순위, 설문, 추천 목록, 매칭 분석, 조율 채팅, 매칭 완료 홈) |
| 사용자 테스트 | 전체 서비스에서 Google 로그인 → 테스트 시작 화면                   | 로그아웃 후 다음 참여자 로그인                                                                     |

- `처음부터`: 같은 참가자 세션에서 시도 번호(`attempt`)를 올리고 처음부터.
- `다음 참가자`(진행자 메뉴): 새 세션. 이전 사람의 우선순위·답변·대화·완료 상태를 보지 않는다(이전 세션 기록은 지우지 않는다).
- `다음 참가자`(체험 채팅의 매칭 완료 버튼, 2026-11-20 변경): 같은 사람의 우선순위·답변은 그대로 두고 대화와 매칭만 지운 뒤 룸메이트 목록으로 간다. 방금 매칭한 후보는 이 세션에서 목록에 나오지 않는다(`처음부터`나 새 참가자에서 다시 나온다).
- 장면 이동은 경로만 바꾸지 않고 그 장면에 필요한 상태(공통 기본 정보, 촬영용 우선순위, 예시 답변, 체험 채팅)를 먼저 준비한다.
- 새로고침하면 진행 중인 체험(우선순위, 답변, 채팅, 매칭)이 복구된다.
- 사용자 테스트의 `시간이 없어서 그냥 둘러볼게요`는 이제 핵심 체험으로 전환한다. 상단 전환이 생겨 기존 `둘러보기` 배너와 버튼은 이 빌드에서 숨겼다.

## 5. 이번에 구현하지 않은 것 (백엔드 의존 또는 후속)

- **게스트 로그인 기반 개인 설문 체험**: BE dev의 `POST /api/auth/guest-login`은 배포·활성화 여부를 확인하지 않았고 FE에 연결하지 않았다. 현재 개인 설문 기반 경로는 사용자 테스트(실제 Google 로그인)뿐이다. 연결하려면 배포 서버에서 응답 계약과, 이미 온보딩이 끝난 게스트의 우선순위를 `PUT /api/me/survey`에 함께 보내는 경로를 확인해야 한다.
- **피드백**: 체험 모드(로그인 없음)에서는 피드백 문항이 나오지 않는다. 기존 피드백은 로그인한 참여자 기준이다. 체험 채팅 안건 완료 뒤의 `채팅 조율 체험의 도움` 문항, 목적별 켜기·끄기(촬영 끔), 결과 출처·채팅 방식 기록은 후속 작업이다.
- **피드백 수집 서버**, **체험 회차 격리와 후보 접근 제한**, **세션 범위 초기화**, **심사 세션별 상대 계정 배정**, **서버 자동 상대**, **합의문 자동 생성**: 백엔드 작업이 필요하다. 일반 초기화 버튼은 전역 `POST /api/auth/dev-reset`을 부르지 않는다.
- 예시 후보는 기존 샘플 데이터(후보 여러 명)를 그대로 쓴다. 요청서의 3명 구성으로 줄이지 않았다.
- 체험 모드에서 새로고침하면 설문 진행 위치(몇 번 문항인지)는 처음으로 돌아간다. 답한 내용은 복구된다.

## 6. 백엔드 담당자에게 필요한 작업

1. 게스트 로그인 배포 여부와 응답(`next_step`, 토큰), 게스트가 우선순위를 설문 저장과 함께 보내는 계약 확인.
2. 체험/테스트 회차 격리: 추천·상세·분석·신청·채팅 접근 범위를 회차 단위로 제한.
3. 피드백 수집 API(`docs/user-test/backend-contract.md` 제안)와 운영자 조회·추출.
4. 권한과 범위를 제한한 세션 초기화(전역 dev-reset 대체).
5. 선택: 서버 자동 상대(자동 상대 표시, 서버 권한으로 메시지·확정), 합의문 생성·저장·조회.

## 7. 심사 계정 준비

- 전체 서비스 검증은 심사위원 계정 A와 팀원 계정 B를 서로 다른 기기 또는 독립된 브라우저 세션에서 쓴다. 같은 학교·성별·기숙사/방 타입 조건을 만족해야 서로 추천된다.
- 상대 계정 하나를 여러 심사 세션이 같이 쓰면, 한 세션의 최종 확정이 다른 세션의 추천·채팅을 끝낸다. 세션마다 다른 상대 계정 쌍을 준비한다.
- 학교 계정이 없는 심사위원은 Google 로그인 경로를 통과하지 못한다. 게스트 경로를 연결하더라도 학교 인증·기본 정보 입력 검증과 따로 기록한다.

## 8. 검증

- `tsc -b`, `eslint`, 전체 테스트 556개 통과(`src/lib/experience/experience.test.tsx` 12개 포함).
  - 체험 빌드라도 체험 모드에서는 `fetch`를 한 번도 부르지 않는다.
  - 채팅 상태 전이, 중복 클릭·지난 타이머의 중복 메시지 방지, 화면 이탈 시 예약 응답 취소.
  - 안건 매칭과 예시 두 사람 전환, 다음 참가자·처음부터.

- 실행하지 못한 검증: 사용자 테스트(실제 Google 로그인)에서 실제 분석 → 체험 채팅 경로, 실제 두 계정 채팅·최종 확정, 게스트 로그인.

## 9. 2026-11-20 디자인 정리

- 체험 시작 화면은 제목(로그인 없이 복작복작을 처음부터 끝까지 체험해 보세요)과 체험 시작하기만 가운데에 둔다.
- 모드 전환 확인 창은 마이페이지 설문조사 다시 하기와 같은 확인 창(ConfirmDialog)을 쓴다.
- 예시 답변으로 건너뛰기는 질문 화면에서만, 답변 영역(베이지 시트) 오른쪽 위 3px 위에 둔다. STEP 상황 화면에는 없다.
- 체험 채팅은 기존 채팅방 디자인(Figma 1715:38109)을 그대로 쓴다: AI 챗봇 안건 카드(미정/확정), 상대·내 말풍선, 카드 안 다음안건으로·매칭확정 하기와 같은 확인 창, 🎉 매칭이 확정되었습니다. 입력창 자리에는 보낼 답장을 고르는 버튼이 나온다.
- 이 빌드(`.env.usertest`)의 전체 서비스는 main과 똑같이 동작한다(2026-11-20 요청). 사용자 테스트 레이어(`VITE_USER_TEST`)는 꺼 두었다. 사용자 테스트를 다시 쓰려면 `VITE_USER_TEST=true`로 바꾼다.
